## 一、项目整体认知

### 项目定位
一个基于 **Spring Boot 3.5.7 + Java 21** 的 **AI Agent 后端系统**，前端为 Vue 3（`../frontend/my-agent-frontend`）。系统提供两大 AI 交互模式：

| 模式 | 实现 | 说明 |
|---|---|---|
| **MyApp（对话助手）** | Spring AI `ChatClient` + RAG | 同步/流式/SSE 三种方式，虚拟线程解决 MCP 阻塞 |
| **MyAgent（ReAct 自主智能体）** | 自定义四层 Agent 框架 | think+act 循环、工具调用、结构化 SSE 事件推送 |

### 模块职责划分

```
space.huyuhao.myagent
├── agent/            # 自定义 ReAct Agent 框架（BaseAgent→ReActAgent→ToolCallAgent→MyAgent）
├── app/MyApp.java    # ChatClient 对话助手（流式/同步）
├── rag/              # Milvus 向量存储、文档分片、RAG 注入
├── mcp/              # 用户级 MCP 工具动态管理、手写 Streamable HTTP transport
├── model/            # ModelEnum 枚举、ModelRouter 路由、UserChatModelManager 动态模型
├── chatmemory/       # 三层记忆（Redis / Kryo 文件）
├── service/          # 向量搜索/嵌入/索引/文档处理等
├── context/          # ThreadLocal + 跨线程 userId 映射
├── interceptor/      # JWT 认证
└── tool/             # 自定义工具（文件操作/资源下载/终止循环）
```

### 技术栈
- **语言/框架**：Java 21、Spring Boot 3.5.7、Spring AI 1.0.0-M6
- **LLM 接入**：阿里 DashScope（`spring-ai-alibaba`）、DeepSeek（`spring-ai-openai`，OpenAI 兼容）
- **向量数据库**：Milvus（主）+ PGVector（备）+ SimpleVectorStore（内存备）
- **数据存储**：MySQL（MyBatis Plus）、Redis（Lettuce 连接池）、Milvus + etcd + MinIO
- **流式**：WebFlux（reactive 流式响应）、Servlet（SseEmitter）
- **认证**：JWT（jjwt 0.12.6）+ BCrypt 密码加密
- **其他**：MCP（Model Context Protocol）、DashScope text-embedding-v3 嵌入、Kryo 序列化、Hutool

## 二、核心业务流程梳理

**ReAct Agent 执行链路（最核心）：**
```
用户请求 /ai/manus/chat?model=...&modelName=...
  → AiController.doChatWithManus()
    → UserChatModelManager.getChatModel()   // 按用户动态获取 ChatModel
    → UserMcpToolManager.getToolsForUser()  // 按用户加载 MCP 工具
    → MyAgent.create()                      // 组装四层 Agent
    → myAgent.runStream()                   // SSE 流式执行
        → CompletableFuture.runAsync()      // 异步线程
        → injectRagContext()                // 向量检索注入系统提示词
        → 加载 Redis 历史记忆
        → for (i < 20) executeStepWithEvents()
            → think()   // 流式调 LLM，推 answer 事件
            → act()     // 执行工具，推 tool_call/tool_result 事件
        → persistNewMessages()  // 结构化事件落库
```

## 三、技术亮点挖掘（筛选后 Top 5）

### 🔥 亮点一：自定义 ReAct 智能体框架 + 结构化 SSE 事件流

```
技术亮点：
    自定义实现 ReAct（Reasoning + Acting）智能体框架，绕过 Spring AI 内置工具调用机制，
    自行维护消息上下文与工具执行循环，并通过结构化 SSE 事件流将思考/工具调用/结果分开展示给前端。

简历描述：
    设计并实现自定义 ReAct 智能体框架（四层继承：BaseAgent→ReActAgent→ToolCallAgent→MyAgent），
    基于"思考-行动"循环 + ToolCallingManager 手动工具执行，屏蔽不同 LLM 提供商的工具调用差异，
    将思考过程与工具调用过程拆分为结构化事件经 SSE 实时推送前端，实现 Agent 全流程可视化。

技术背景：
    Spring AI 提供了 ChatClient 内置的工具调用能力，但存在两个痛点：
    1. 内置机制把思考文本、工具调用、工具结果混在一起，前端无法分开展示"模型在想什么"；
    2. 不同 provider（DashScope 的 proxyToolCalls / DeepSeek 的 OpenAI 兼容）工具调用语义不同，难以统一。
    项目目标是构建一个可自主规划、调用多工具、步骤可回放的"Manus 式"智能体。

解决问题：
    - 如何在不依赖框架内置机制的前提下，实现多步工具调用循环？
    - 如何让前端实时看到 Agent 的思考过程、选用了哪些工具、工具返回了什么？
    - 如何兼容 DashScope 与 DeepSeek 两种完全不同的工具调用协议？

实现方案：
    1. 四层抽象：BaseAgent（状态机+SSE 生命周期）→ ReActAgent（think/act 抽象+事件封装）
       → ToolCallAgent（具体工具执行）→ MyAgent（业务组装，maxSteps=20）。
    2. think() 使用 ChatClient .stream() 逐块消费，将文本实时推给 onToken 回调，
       并聚合完整消息与 tool_call；act() 通过 ToolCallingManager.executeToolCalls() 手动执行工具，
       proxyToolCalls=true / internalToolExecutionEnabled(false) 关闭框架自动执行。
    3. executeStepWithEvents() 将每个步骤产出为独立事件：
       step_start / think / tool_call / tool_result / step_end / answer / finish / error / max_steps，
       经 SseEmitter 顺序推送，工具结果过长自动截断（MAX_TOOL_RESULT_LENGTH）。
    4. 特殊场景处理：仅调用 doTerminate 时判定为收尾，不把最终回答误报为"思考过程"；
       无工具调用时直接从 finalAnswerText 产出 finish 事件。

核心代码/实现细节：
    // ToolCallAgent.think() —— 流式思考，逐字推送并聚合 tool_call
    Flux<ChatResponse> responseFlux = getChatClient().prompt(prompt)
            .system(getSystemPrompt()).tools(availableTools).stream().chatResponse();
    responseFlux.doOnNext(chunk -> {
        if (text 非空) { fullText.append(text); onToken.accept(text); }
        if (chunkToolCalls 非空) toolCallResponse.set(chunk);
    }).blockLast();
    // 组装 ChatResponse，供 act()/getToolCallInfo() 使用
    this.toolCallChatResponse = new ChatResponse(List.of(new Generation(assistantMessage)));

    // ToolCallAgent.act() —— 手动执行工具
    ToolExecutionResult r = toolCallingManager.executeToolCalls(prompt, toolCallChatResponse);
    setMessageList(r.conversationHistory());   // 自己维护上下文

相关代码位置：
    - agent/model/BaseAgent.java        (runStream / executeStepWithEvents / injectRagContext)
    - agent/model/ReActAgent.java       (think/act 抽象、事件流封装、isOnlyTerminateToolCall)
    - agent/ToolCallAgent.java          (think/act 具体实现、getToolCallInfo)
    - agent/MyAgent.java                (四层组装、maxSteps=20、RedisChatMemory)
    - agent/model/AgentStepEvent.java   (结构化事件模型)
    - controller/AiController.java:132  (doChatWithManus 入口)

调用链：
    AiController.doChatWithManus → MyAgent.create → myAgent.runStream
      → CompletableFuture.runAsync（异步线程）
        → 加载 Redis 历史 → for(≤20步) executeStepWithEvents
          → think()（LLM 流式，answer 事件逐字推送）
          → 有工具 → act()（ToolCallingManager 执行）→ tool_call/tool_result 事件
          → 无工具/doTerminate → finish 事件
        → 全量事件持久化到 Redis 会话记忆

工程价值：
    - 构建了可复用的 Agent 框架，支持任意 provider 插拔，后续接新模型仅需扩展 ModelEnum；
    - 结构化事件流让复杂 Agent 过程对用户透明可解释，提升产品体验与可调试性；
    - 该框架是同类"自主智能体"产品（如 Manus、AutoGPT）的核心架构，面试含金量高。

面试追问：
1. 为什么不用 Spring AI 内置的工具调用，而要自己实现？
   建议回答：内置机制把思考文本、工具调用和工具结果揉在一个 ChatResponse 里，前端无法区分展示；
   而且不同 provider 的工具调用协议不同（DashScope 用 proxyToolCalls，DeepSeek/OpenAI 兼容协议），
   统一封装后可以由我们控制消息上下文与事件流转，便于多步推理和结构化落库。
2. 如何保证 Agent 不会无限循环？
   建议回答：三个保险——maxSteps=20 硬上限、TerminateTool.doTerminate() 主动终止、
   以及无工具调用时自动判定 FINISHED。超过步数发 max_steps 事件并正常收尾。
3. think() 里 blockLast() 在流式场景下不会阻塞吗？
   建议回答：这里在 runStream 的 CompletableFuture 异步线程（非 Netty 线程）上执行，不违反 Reactor 线程约束；
   而 MyApp 的 ChatClient 流式路径里阻塞 MCP 是另一个问题，用虚拟线程包装解决（见亮点二）。
4. 如何支持不同的 LLM 提供商？
   建议回答：抽象出 chatOptions，由 ModelRouter.createChatOptions() 按 provider 生成专属选项——
   DashScope 用 withProxyToolCalls(true)，DeepSeek 用 internalToolExecutionEnabled(false)，
   Agent 层通过 ToolCallingManager 统一手动执行，屏蔽差异。
5. Agent 每步耗时可能很长，SSE 连接怎么处理？
   建议回答：SseEmitter 设 300s 超时，客户端断开用 safeSend/safeComplete 吞异常，
   保证 Agent 在后台继续执行并把最终结果落库，不因前端断开而丢失。
```

### 🔥 亮点二：WebFlux 流式对话中 MCP 阻塞调用的虚拟线程隔离

```
技术亮点：
    定位并解决 Spring AI 流式对话中 MCP 工具调用在 Netty 线程上 block() 抛异常的问题，
    利用 Java 21 虚拟线程为工具回调构建代理包装层，实现"阻塞调用"与"响应式线程"的安全隔离。

简历描述：
    解决 Spring AI 流式（WebFlux/Netty）链路中 MCP 同步工具调用导致的线程阻塞异常，
    基于 Java 21 虚拟线程为工具回调构建代理包装层，将阻塞调用迁移至虚拟线程执行，
    在不改动框架调度链的前提下消除了 Netty 线程上非法 block() 的问题，保证流式对话稳定可用。

技术背景：
    SSE 流式接口基于 WebFlux/Netty 非阻塞模型，Reactor 严禁在 reactor-http-nio 线程上调用
    block()/blockFirst()/blockLast()。而 MCP 客户端采用同步模式 McpSyncClient，
    callTool() 内部就是 Mono.block() 等待返回。当模型在流式过程中决定调用 MCP 工具时，
    Spring AI 内部 AbstractToolCallSupport 在 Netty 线程上同步调用 SyncMcpToolCallback.call()，
    直接触发 Reactor 线程安全检查，抛 IllegalStateException。

解决问题：
    - 阻塞调用在响应式线程上被执行，如何在不改框架的前提下隔离？

实现方案：
    用虚拟线程执行器包装每个 MCP 工具回调：wrapper.call() 把真实调用 submit 到
    虚拟线程执行器并 .get(120s) 等待，使 Mono.block() 发生在虚拟线程上（Reactor 允许），
    Netty 线程则通过 LockSupport.park 合法挂起等待。
    关键论证：subscribeOn/publishOn 无效，因为工具执行是框架内部同步调用，不经过 Reactor 调度链，
    必须在工具回调边界做线程隔离。

核心代码/实现细节：
    // MyApp.wrapForBlocking()
    FunctionCallback[] wrapForBlocking(FunctionCallback[] originals) {
        return Arrays.stream(originals).map(tool -> new FunctionCallback() {
            public String call(String toolInput) {
                try {
                    return blockingExecutor.submit(() -> tool.call(toolInput))
                            .get(120, TimeUnit.SECONDS);   // 虚拟线程上执行真实阻塞调用
                } catch (Exception e) {
                    throw new RuntimeException("MCP tool call failed: " + tool.getName(), e);
                }
            }
            // getName/getDescription/getInputTypeSchema 委托原工具
        }).toArray(FunctionCallback[]::new);
    }

相关代码位置：
    - app/MyApp.java:152 (wrapForBlocking) / :123 (doChatByStream)
    - controller/AiController.java:101 (doChatWithMyAppSseEmitter)
    - 项目问题解决/SpringAI-MCP流式调用阻塞问题.md (完整问题分析与方案)

调用链：
    SSE 请求 → Netty 线程 → ChatClient.stream() → 模型返回 tool_call
      → AbstractToolCallSupport.handleToolCalls → wrapper.call()
        → Future.get() 挂起 Netty 线程（park，合法）
        → 虚拟线程执行 tool.call → McpSyncClient.callTool → Mono.block()（虚拟线程，允许）
      → 返回结果给 Netty 线程

工程价值：
    - 深入理解响应式编程的线程模型约束与"阻塞/响应式边界"概念；
    - 虚拟线程以极低挂起成本做"阻塞转隔离"的胶水层，是 Java 21 的最佳实践案例；
    - 踩坑文档完整，直接体现了排障能力。

面试追问：
1. 为什么 subscribeOn 解决不了这个问题？
   建议回答：subscribeOn 只决定 Reactor 操作符链订阅发生的线程，而工具执行是 Spring AI
   在模型返回 tool_call 后同步调用的，不经过 Reactor 调度链，所以切调度器对它无效。
   必须在工具回调这个"框架边界"做线程隔离。
2. 虚拟线程和平台线程在这个场景下的区别？
   建议回答：虚拟线程挂起/恢复由 JVM 调度，成本远低于平台线程的上下文切换；
   百万级虚拟线程常驻成本低，适合包装大量同步阻塞调用。这里用专用执行器隔离也便于超时控制。
3. 为什么不直接让 MCP 走异步 API？
   建议回答：McpSyncClient 是项目选用的同步客户端，改造异步 client 涉及框架内部改动、成本高；
   虚拟线程包装是侵入最小、风险最低的边界方案，符合"不改框架"的约束。
4. 120 秒超时是怎么定的？
   建议回答：针对 MCP 工具实际调用耗时设定，长任务（如地图 POI 查询）留足余量；
   超时后抛异常由外层统一处理，不会无限挂起。
```

### 🔥 亮点三：多用户动态 LLM 路由与按需构建缓存

```
技术亮点：
    将 LLM 配置从"全局写死"改造为"用户级动态路由"：每个用户可自配各供应商 api-key 与模型列表，
    后端按 (userId, provider, modelName) 动态构建 ChatModel 并做并发安全的缓存管理。

简历描述：
    设计并实现用户级动态 LLM 路由与缓存体系，支持每个用户独立配置多供应商（DashScope/DeepSeek）
    API Key 与模型，基于"每用户锁 + 双重检查"构建 ChatModel 缓存，配置变更即时失效重载，
    实现多租户下模型资源的高效复用与安全隔离。

技术背景：
    最初 api-key 与模型名全局写死在 application.yml，所有用户共用一套。产品要求：
    每个登录用户用自己的 key、选自己的模型，未配置时强制提示配置（不使用系统默认 key）。

解决问题：
    - 如何按用户动态创建不同 provider、不同模型名的 ChatModel（Bean 无法预注册）？
    - 高并发下如何避免同一 key 重复构建 ChatModel？
    - 配置变更后如何让已有连接/模型失效？

实现方案：
    1. 数据模型：user_llm_config（每供应商一 key）+ user_llm_model（每供应商多模型名），
       唯一索引 (user_id, provider) 与 (user_id, provider, model_name)。
    2. UserChatModelManager.getChatModel(userId, model, modelName)：
       查库 → 校验 enabled → 按 provider 分支构建（DashScope vs DeepSeek）→
       以 key=userId:provider:modelName 缓存，每用户锁 + 双重检查防重复构建。
    3. invalidate(userId)：配置增删改/启停后按前缀清除该用户全部缓存，下次请求重建。
    4. testConnection：临时构建（不入缓存）调用 chatModel.call(ping) 验证 key 可用。
    5. api-key 安全：明文存库、接口返回脱敏（****后4位）、日志不打印。

核心代码/实现细节：
    public ChatModel getChatModel(Long userId, ModelEnum model, String modelName) {
        // ... 校验 user_llm_config 存在且 enabled == 1，否则抛 LlmNotConfiguredException
        String key = userId + ":" + provider + ":" + modelName;
        ChatModel cached = modelCache.get(key);
        if (cached != null) return cached;
        Object lock = userLocks.computeIfAbsent(userId, k -> new Object());
        synchronized (lock) {                    // 每用户锁 + 双重检查
            cached = modelCache.get(key);
            if (cached != null) return cached;
            ChatModel chatModel = buildChatModel(provider, config.getApiKey(), modelName);
            modelCache.put(key, chatModel);
            return chatModel;
        }
    }

相关代码位置：
    - model/UserChatModelManager.java      (核心：getChatModel/invalidate/testConnection/buildChatModel)
    - model/ModelEnum.java / ModelRouter.java (provider 抽象与 ChatOptions 生成)
    - config/DeepSeekConfig.java            (DeepSeek ChatModel 手动构建，排除自动配置冲突)
    - exception/LlmNotConfiguredException.java
    - controller/UserLlmConfigController.java、service/impl/UserLlmConfigServiceImpl.java
    - docs/2026-08-20-用户自定义LLM配置方案.md、docs/多模型切换方案.md

调用链：
    前端选择模型(provider:modelName) → /ai/my_app/chat/sse/one?model=qwen&modelName=qwen-max
      → MyApp.doChatByStream → UserChatModelManager.getChatModel(userId, model, modelName)
        → 缓存命中直接返回；未命中 → 查 user_llm_config → 锁内构建 → 写缓存
      → 未配置 → 抛异常 → 返回提示分块 / error 事件（用户消息不持久化，避免无限轮询）

工程价值：
    - 把"框架静态 Bean 装配"升级为"运行时动态构建"，是多租户 SaaS 化的典型改造；
    - 每用户锁粒度细、双重检查避免重复构建，兼顾正确性与性能；
    - 未配置即明确提示而非静默降级，产品行为清晰可控。

面试追问：
1. 缓存 key 为什么带 userId 和 modelName？
   建议回答：不同用户 key 不同、同一供应商不同模型也是不同 ChatModel，key 必须能唯一定位，
   否则会串用户或串模型，造成 api-key 泄漏或模型错乱。
2. 为什么用每用户锁而不是全局锁？
   建议回答：全局锁在大量用户同时首调时会串行化，吞吐低；每用户锁只串行化同一用户的构建，
   不同用户可并行构建，且配合双重检查进一步降低锁竞争。
3. 配置改完后已有的长连接/MCP 客户端怎么处理？
   建议回答：invalidate(userId) 统一失效——清模型缓存，MCP 侧 UserMcpToolManager.invalidate 清
   工具缓存并关闭客户端长连接，下次请求全部重建。
4. 引入 spring-ai-openai 时遇到什么坑？
   建议回答：会自动激活 OpenAiAutoConfiguration，要求 spring.ai.openai.api-key 并创建不需要的
   embedding bean，启动即失败；通过在启动类 exclude 该自动配置、DeepSeek 模型手动构建解决。
```

### 🔥 亮点四：用户级动态 MCP 工具管理（协议探测 + 手写 Streamable HTTP transport）

```
技术亮点：

    自动探测服务协议（Streamable HTTP / 传统 SSE），并手写 Streamable HTTP 传输层客户端。

    设计并实现用户级动态 MCP（Model Context Protocol）工具接入框架，支持用户自配 MCP 服务
    并动态注入到 Agent 工具链；基于 JSON-RPC ping 自动探测服务协议并回退，
    手写 Streamable HTTP 传输层（会话 ID 管理与 SSE 响应解析），单服务故障隔离，
    实现外部工具生态的灵活扩展与用户隔离。

技术背景：
    MCP 是让 LLM 通过标准化协议调用外部工具（如高德地图）的开放标准。项目要让"每个用户"
    能自行添加 MCP 服务，且服务协议不确定（有的支持 Streamable HTTP，有的只支持传统 SSE）。

解决问题：
    - 协议不确定：如何判断一个 URL 走哪种传输协议？
    - 官方 SDK 的 Streamable transport 依赖 WebFlux 容器，与当前 Servlet/阻塞模型不匹配怎么办？
    - 如何按用户隔离、缓存 MCP 长连接并做到故障不扩散？

实现方案：
    1. 协议探测：向 URL POST 一个 JSON-RPC ping，返回合法 JSON-RPC 或 event-stream 即判定
       支持 Streamable HTTP，否则回退传统 HttpClientSseClientTransport。
    2. 手写 HttpClientStreamableClientTransport：实现 ClientMcpTransport 接口，
       用 Java 原生 HttpClient.sendAsync + Mono.fromFuture 适配响应式，维护 AtomicReference 会话 ID，
       解析 SSE 分块响应（按空行切块、提取 data 字段），400+ 状态码转为 McpError。
    3. 连接管理：clientCache(key=userId:serverId) + toolsCache(userId)，每用户锁 + 双重检查；
       建连失败只记日志并更新连接状态字段(1成功/2失败)，返回 null 跳过，不拖垮整体；
       invalidate(userId) 失效并关闭连接，@PreDestroy 全量释放。

核心代码/实现细节：
    // 协议探测
    private ClientMcpTransport createTransport(String url) {
        return isStreamableHttp(url)
            ? new HttpClientStreamableClientTransport(url)
            : new HttpClientSseClientTransport(url);
    }
    private boolean isStreamableHttp(String url) {
        // POST {"jsonrpc":"2.0","id":1,"method":"ping","params":{}}，
        // content-type 含 json/event-stream 或 body 含 "jsonrpc" 即判定支持
    }
    // 手写 transport 发送消息 + 会话 ID 管理
    String sid = sessionId.get();
    if (sid != null) builder.header("Mcp-Session-Id", sid);
    return Mono.fromFuture(httpClient.sendAsync(...)).flatMap(response -> {
        response.headers().firstValue("Mcp-Session-Id").ifPresent(sessionId::set);
        List<JSONRPCMessage> messages = parseResponse(response.body(), contentType);
        messages.forEach(msg -> handler.apply(Mono.just(msg)).subscribe());
        return Mono.empty();
    });

    - service/impl/UserMcpServerServiceImpl.java / mapper/UserMcpServerMapper.java
    - controller/UserMcpServerController.java
    - docs/用户自定义MCP工具配置方案.md

调用链：
    用户配置 MCP 服务 → 存库(user_mcp_server) → 对话请求
      → UserMcpToolManager.getToolsForUser(userId) → 缓存命中或建连

    - 打通了"用户自服务扩展外部工具"的产品形态，是 Agent 生态扩展的通用底座；
    - 手写 transport 体现对 MCP 协议栈（JSON-RPC 2.0、SSE、会话管理）的深入理解；
    - 连接缓存 + 故障隔离 + 优雅关闭，具备生产级质量。

面试追问：
1. Streamable HTTP 和传统 SSE 传输的核心区别？
   建议回答：Streamable HTTP 是单端点、请求-响应可同时支持 JSON 和 SSE 流式返回，
   用 Mcp-Session-Id 维护会话；传统 SSE 分 initialize/notifications 两个端点，
   需要单独的 SSE 订阅连接。项目通过 ping 探测自动区分。
2. 为什么不用官方 HttpClientStreamableClientTransport？
   建议回答：官方实现依赖 Spring WebFlux 的 WebClient 及容器环境，而项目部分链路基于
   Servlet/阻塞模型；手写实现基于 Java 原生 HttpClient，避免引入多余依赖并适配现有线程模型。
3. 如何防止一个用户坏 MCP 服务影响其他用户？
   建议回答：连接按 (userId, serverId) 隔离缓存；单个服务建连失败仅记日志、更新状态、跳过该服务，
   不影响其他服务与其他用户；整体降级为"少一个工具而非全挂"。
4. 连接状态如何反馈给用户？
   建议回答：建连结果写入 user_mcp_server.connect_status 字段（1成功/2失败），
   前端列表页实时展示；并提供 testConnection 预检、listTools 调试工具列表。
```

### 🔥 亮点五：多租户 RAG 管道（自定义 Milvus 向量存储 + 文档分片 + 标量过滤）

```
技术亮点：
    构建完整的多租户 RAG（检索增强生成）管道：上传→分块→向量化→Milvus 检索→注入系统提示词，
    自研 Spring AI VectorStore 接口的 Milvus 实现，支持配置化切换向量库，实现用户数据隔离。

简历描述：
    设计并实现基于 Milvus 的多租户 RAG 管道，自定义 VectorStore 实现完成文档分片
    （Markdown 标题分节+段落切分+重叠与句界优化）、DashScope text-embedding-v3 向量化、
    Milvus 相似度检索与 Spring AI 过滤表达式到 Milvus 标量过滤的转换；
    按 userId 元数据实现多用户数据隔离，向量库支持 milvus/pgvector/simple 配置化切换，
    支撑 Agent 与对话双模式的上下文增强。

技术背景：
    需要让 Agent 基于用户上传的私有文档回答。三套向量库方案（Milvus/PGVector/内存）要能
    配置化切换；Milvus 的原生 SDK 与 Spring AI 的 VectorStore 接口需要桥接。

解决问题：
    - 如何把 Spring AI 抽象的 VectorStore 接口适配到 Milvus SDK（字段、过滤、删除语义不同）？
    - 分块策略如何保证检索质量（标题语义、边界不切断句子）？
    - 多用户文档如何在向量库中隔离并安全删除？

实现方案：
    1. MilvusVectorStore 实现 VectorStore 接口：add（识别预分片标记跳过二次分片）、
       similaritySearch（L2 距离 + nprobe=10 + 相似度阈值过滤 similarity=1/(1+score)）、
       delete（id 列表或过滤表达式）。
    2. 过滤表达式翻译器：把 Spring AI 的 Filter.Expression 语法树（AND/OR/EQ/IN/NOT 等）
       switch 递归翻译为 Milvus 表达式，如 metadata["userId"] == 1。
    3. DocumentChunkService 分层分片：Markdown 标题(#~######)分节保留语义 → 段落边界切分 →
       超过 maxSize 时带重叠(overlap)续切，重叠部分在句号/问号/感叹号处智能截断避免切句子。
    4. 多租户：metadata 写入 userId/_source/_file_name/chunkIndex/totalChunks；
       搜索时构造 Filter 强制 userId 相等；删除时用 AND 条件(userId + _source)精准删；
       还通过 UUID.nameUUIDFromBytes 生成确定性文档 ID 避免重复插入。
    5. 配置化切换：vector.store.type=milvus/simple/pgvector，@ConditionalOnProperty 装配，
       生产环境默认 Milvus，避免把全部向量加载进 JVM 堆。

        return switch (exp.type()) {

面试追问：
1. L2 距离的 score 和相似度怎么换算？
   建议回答：Milvus 返回 L2 欧氏距离，距离越小越相似；用 similarity = 1/(1+distance) 归一化到 (0,1]，
   再和阈值比较过滤低相关结果，避免"答非所问"。
2. 分片策略为什么这么设计？
   建议回答：先按 Markdown 标题分节保留每块的语义归属（存 title 进 metadata）；
   超长章节按段落切，避免在句子中间切断；段落拼到 maxSize 超限时带 overlap 续切，
   且 overlap 在句末标点处截断，保证接续处上下文连贯、检索不丢关键信息。
3. 多租户隔离是怎么做的？
   建议回答：元数据 userId 写进每条向量记录；检索时把 userId 编译进 Milvus 标量过滤表达式强制过滤；
   删除用 AND(userId, _source) 保证只能删自己的文档；MySQL 侧 selectByUserIdAndId 也校验所有权。
4. 为什么文档 ID 用 nameUUIDFromBytes 而不是随机？
   建议回答：确定性 ID 使"同一用户同一文件同一分片"重复上传时 ID 稳定，配合幂等入库可避免向量库重复记录，
   也便于按文件精准定位删除。
5. 生产环境为什么选 Milvus 而非 SimpleVectorStore？
   建议回答：SimpleVectorStore 把所有文档+1024维向量常驻 JVM 堆，内存 500MB+；
   切 Milvus 后向量数据放外部进程，纯配置切换，堆内存显著下降（见内存优化方案）。
```
